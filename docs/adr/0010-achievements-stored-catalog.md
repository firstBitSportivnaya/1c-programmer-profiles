# Достижения хранятся: каталог из 30, выдача строкой

ADR 0006 закрепил: ачивки не хранятся, их видно по текущим приёмкам не отменённых ИПР. Этого хватает четырём следствиям, но не продукту: добавить или изменить достижение вручную нельзя, видов ровно четыре и они заданы кодом, названия и условия нельзя согласовать с отделом, а список виден только самому сотруднику на `/me/achievements`. Каталог из 30 достижений и ручная выдача требуют хранимых сущностей.

Достижение — запись каталога плюс выдача сотруднику. Каталог отвечает на вопрос «что бывает», выдача — «кому, когда и почему досталось». Очков, уровней и рейтинга нет: достижение не участвует в разрыве, ИПР, пометках и назначении должности.

## Каталог

Таблица `achievements`: `id` — стабильный ключ (slug, первичный ключ), `title`, `description`, `category`, `rule`, `rule_param`, `icon`, `archived`, `updated_at`.

- Ключ — единственное, на что ссылается выдача. Он не меняется после появления в базе: переименование названия ключ не трогает.
- Категория — закрытый список: `idp`, `competency`, `career`, `mentoring`, `contribution`.
- `rule` — `manual` или ключ автоматического правила из закрытого списка. `rule_param` уточняет правило (например, id должности) и у `manual` пуст.
- `icon` — имя глифа из общего набора `src/components/skill-icons.tsx`. Иконка декоративная, название она не заменяет.
- Запись не удаляют: её скрывают `archived = 1`. Уже выданное достижение остаётся в списке сотрудника, из каталога уходит только предложение выдать его снова.
- Каталог правит админ. Сотрудник и гость форм не видят и действий не выполняют.

Состав каталога — `seed/achievements.json`, ровно 30 записей. `npm run check:seed` проверяет количество, уникальность ключа и названия, непустые название и описание, категорию, правило, иконку и параметр правила. Правки каталога админом seed не перезаписывает: он только добавляет недостающие ключи.

## Выдача

Таблица `employee_achievements`: `employee_id`, `achievement_id`, `source` (`auto` | `manual`), `rule_key` — снимок правила на момент выдачи, `source_ref` — необязательная ссылка на объект, из-за которого выдано (сейчас это id ИПР), `granted_at`, `granted_by_id`, `revoked_at`, `revoked_by_id`, `revoke_reason`.

- Первичный ключ `(employee_id, achievement_id)`. Повторная выдача не создаёт вторую строку, а обновляет ту же: снимает отзыв и ставит новую `granted_at`.
- Отзыв не удаляет строку. Он ставит `revoked_at`, при ручном отзыве ещё `revoked_by_id` и причину. Так видно, что достижение было и когда его сняли.
- `granted_by_id` заполнен только у ручной выдачи, у автоматической там `NULL` — выдала система. Отозвать вручную можно и автоматическое достижение; тогда отзыв подписан сотрудником.
- Достижение видно только владельцу. Страницы достижений с чужим id нет. В карточке сотрудника `/people/{id}` его действующие выдачи видит тот, кому доступна карточка: сам сотрудник, прямой руководитель и админ; выдавать и отзывать там может только тот, кто может менять карточку.

## Ручная выдача

Админ выдаёт достижение любому сотруднику. Руководитель — только своим прямым подчинённым: та же оргсвязь, по которой он принимает строки ИПР (ADR 0003, 0006). Сотрудник не выдаёт и не отзывает ничего, в том числе себе.

Ручное достижение не отзывается автоматически ни при каких изменениях в ИПР, должности или пометках. Снимают его админ или руководитель подчинённого, с причиной.

## Автоматическая выдача

Правила — закрытый список ключей в `src/lib/achievement-rules.ts`. Правило — предикат по текущим данным: ИПР и их строки, приёмки, справочник компетенций, профиль текущей должности, должность и оргсвязь. Личные пометки условием не служат: это заметка сотрудника для себя (ADR 0007). Дат приёма на работу в базе нет, поэтому правил «стаж» и «год в должности» в каталоге нет: их нечем проверить.

Список правил:

| Ключ | Условие |
|---|---|
| `idp.first-accepted-item` | есть хотя бы одна принятая строка в не отменённом ИПР |
| `idp.items-3`, `idp.items-10` | принято не меньше 3 или 10 строк за всё время |
| `idp.competency-confirmed` | все строки хотя бы одной компетенции плана приняты |
| `idp.pool-confirmed` | все компетенции пула хотя бы одного плана подтверждены |
| `idp.completed` | есть выполненный ИПР |
| `idp.completed-2` | выполнено два ИПР |
| `idp.on-time` | выполненный ИПР, все строки со сроком приняты не позже срока |
| `competency.confirmed-3`, `-5`, `-10`, `-20` | подтверждено не меньше 3, 5, 10 или 20 разных компетенций |
| `competency.half-profile` | подтверждена не меньше половины навыков профиля текущей должности (округление вверх) |
| `competency.full-profile` | подтверждены все навыки профиля текущей должности |
| `competency.outside-profile` | подтверждена компетенция вне профиля текущей должности |
| `job.assigned` | сотруднику назначена должность из `rule_param` |
| `manager.direct-1`, `manager.direct-3` | есть 1 или 3 прямых подчинённых |
| `manager.report-idp-completed` | у прямого подчинённого выполнен ИПР |
| `manager.report-competency` | у прямого подчинённого подтверждена компетенция |

Проверка идемпотентна и идёт без планировщика: при каждом изменении, от которого зависит правило (приёмка и снятие приёмки, правка профиля должности, смена должности, оргсвязь), и при открытии `/me/achievements`. Повторное выполнение условия второй строки не даёт.

## Отзыв автоматических

Условие перестало выполняться — автоматическое достижение отзывается, как и в ADR 0006: сняли приёмку, переоткрыли план, сменили должность — ачивка пропала. Строка остаётся с `revoked_at`; вернулось условие — отзыв снимается, `granted_at` обновляется. Ручные выдачи этот механизм не трогает.

Смена правила у записи каталога — тоже изменение условия: сразу после сохранения сверка прогоняется для всех, у кого есть выдача этой записи. Новое правило проверяется как обычно; правило, ставшее `manual`, условия больше не имеет, поэтому автоматические строки отзываются, а ручные остаются. Сменили правило обратно — автоматика выдаст достижение снова, если условие выполняется.

Отзыв автоматического достижения подписан системой (`revoked_by_id = NULL`). Если его снял человек, подпись и причина остаются за человеком, и автоматика строку больше не оживляет: решение человека сильнее предиката.

## Старые четыре

- «Первая принятая строка» → `idp-first-step`.
- «Все компетенции пула подтверждены» → `idp-pool-closed`.
- «ИПР выполнен» → `idp-completed`.
- «Компетенция подтверждена» с id компетенции → в каталог не переносится. Подтверждение конкретной компетенции — свойство плана, а не награда: оно остаётся на `/me/achievements` отдельным блоком «Подтверждённые компетенции», считается по приёмкам и в таблицу выдач не попадает. В каталоге вместо него стоят пороги `competency-3`, `competency-5`, `competency-10`, `competency-20` и одна запись `idp-competency-confirmed` («Компетенция подтверждена», правило `idp.competency-confirmed`): она выдаётся один раз, сколько бы компетенций сотрудник ни подтвердил. Строки выдачи на каждую компетенцию нет, названия подтверждённых компетенций остаются текстом в блоке.

Страница `/me/achievements` показывает выданные и не отозванные достижения каталога, свежие сверху, и блок подтверждённых компетенций под ними. Ссылка строки ведёт на ИПР из `source_ref`; у достижения без плана ссылки нет. Доступ прежний: только своя страница.

`src/lib/achievements.ts` после перехода отдаёт выдачи, а не считает их по приёмкам. Подтверждённые компетенции он считает отдельно, для блока на странице, и в каталог они не попадают.

## Миграция

`migrate()` создаёт обе таблицы и индексы, ничего не пересоздавая, поэтому `ALLOWED_LOSS` не нужен. Сразу после создания каталог дополняется записями из `seed/achievements.json` по ключу: существующие строки не перезаписываются.

Для базы, где достижения раньше вычислялись, миграция однократно записывает выдачи по трём переносимым правилам для всех сотрудников и ставит `source = 'auto'`, `rule_key` и `source_ref`. Достижения не пропадают при обновлении. `scripts/upgrade-base.ts` заполняет обе новые таблицы, чтобы `check:upgrade` видел те же строки до и после.

## Отказ

- Хранить достижение только в коде и выдавать по ключу без каталога: тогда нельзя ни переименовать, ни добавить, ни согласовать список из 30.
- Считать достижения на чтении, как в ADR 0006: ручная выдача и отзыв тогда негде записать, а «выдано давно» и «выдано сегодня» неразличимы.
- Хранить выдачу без отзыва и удалять строку: теряется история, а повторная выдача после ошибки выглядит как первая.
- Разрешить руководителю выдавать любому сотруднику: оргсвязь в продукте ограничивает руководителя прямыми подчинёнными (ADR 0003).

## Проверка

Критерии 1–2 issue #113: ADR и `CONTEXT.md` читаются ревью, каталог — `npm run check:seed`. Миграция, админка, автоматическая выдача и страница проверяются отдельными задачами: `check:upgrade` на снимке базы и e2e на создание, правку, ручную выдачу, отказ сотруднику, повторное выполнение условия и отзыв.
